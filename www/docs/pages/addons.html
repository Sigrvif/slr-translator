User Addons

SLR Translator is modular: everything you see — the translation engines, the RPG Maker parsers, the OCR module — is an addon loaded at startup. The addons that ship with the application are mandatory built-ins living in www/core/; the empty www/addons/ folder next to it exists for your own. Dropping a third-party addon there extends the application with new engines, parsers, UI or tools without touching the core.

How loading works

  • On startup the addon loader scans www/core/ first and www/addons/ second. Every subfolder that contains a package.json is loaded as an addon.
  • Core-first order settles name collisions: if a user addon folder has the same name as a core module, the core one wins and the user addon is ignored.
  • Core modules carry builtin: true in their manifest, which marks them as mandatory — they are always loaded and cannot be removed.

Enabling and removing addons

There is deliberately no addon manager and no enable/disable switch: an addon is active exactly when its folder sits inside www/addons/.

  • Enable an addon: put its folder (the one containing the package.json) into www/addons/ — or open a .tap package with SLR Translator, which extracts it there — and restart SLR Translator.
  • Remove an addon: delete its folder from www/addons/ and restart. That fully removes the addon; only its saved settings remain in data/config.json, which is harmless (and reused if you ever install it again).
  • A broken addon cannot keep the application from starting: failures are logged to data/logs/trans.log and the remaining addons load normally.

The package.json format

{
	"name": "my-addon",          // unique id, case-insensitive
	"title": "My Addon",
	"description": "What it does.",
	"version": "1.0.0",
	"main": "main.js",
	"autoload": true             // true: load every file in the folder
	                             // false: load only files in the "load" array
	// "load": ["main.js"]       // used when autoload is false
}
Never set builtin: true on a user addon — that flag is reserved for the shipped core modules and marks an addon as mandatory.
  • JavaScript files run as the body of an async function with this bound to the addon's own Addon instance — keep a const thisAddon = this; reference at the top, as core modules do.
  • HTML and CSS files in the folder are loaded into the application DOM alongside the scripts. Files whose name starts with ! are registered but never executed — handy for data files you want in thisAddon.files.
  • npm dependencies go into the addon's own node_modules/ folder and are loaded with this.require("module") (or exposed globally with this.globalizeNodeModules()).

What addons can do

  • Register translation engines, file parsers or game engines by extending the base classes in www/js/ — the same mechanism the built-in modules use. An addon is limited only by the application's API: it can add toolbar buttons and dialogs, options pages, context menu entries, own slides in the New Project dialog or whole windows.
  • Expose settings: assigning a schema object to this.optionsForm renders a configuration form in the Options dialog — either as a section in General (optionsDisplay: "general") or as its own top-level tab (optionsDisplay: "tab", how the SEP module does it). Values persist in the application configuration and are read back through thisAddon.config.
  • Addons without settings stay out of the way: an addon only appears in the Options dialog when it actually exposes an optionsForm (or optionsFormHtml) and sets optionsDisplay to "general" or "tab".
  • Add complete new game engines — including engines for non-RPG-Maker games — in pure JavaScript. See Adding a game engine below.
  • Ship their own page in the offline documentation — see Shipping a documentation page below.

Adding a game engine

A game engine addon hooks into three points of the project lifecycle. All of them are optional except createProject and exportHandler — without those two the project cannot be created or written back.

  • Detection — Engines.registerDetector(async (gamepath) => engineId | false) makes the New Project dialog recognize the game. Built-in detectors run first; registered ones afterwards.
  • Project creation — a createProject handler on the engine builds the whole project in JavaScript. When it exists, the PHP backend is not involved at all. It receives {gameFolder, selectedFile, gameEngine, gameTitle, projectId, options} and must resolve to a project object (structure below).
  • Export — the engine's exportHandler(targetPath, options) writes the translation back to the game. It must do the writing itself and return true, which stops the built-in PHP export (that one only understands the RPG Maker formats).
  • Optional: onLoadTrans (patch project data when a saved project opens), onAfterCreateProject (after the project was applied), onCheckProjectExist (validation before creation).

The project object returned by createProject has this shape — data rows are arrays whose first two cells are the original text and the translation:

{
	gameEngine : "myengine",
	gameTitle  : "Some game",
	loc        : "C:/path/to/the/game",      // the game folder
	projectId  : "a1b2c3",
	parser     : "myengine",                 // your parser id
	cache      : { cacheID, cachePath },     // from common.initStaging()
	files      : {
		"story/chapter1.txt" : {
			path      : "story/chapter1.txt",
			dirname   : "story",
			basename  : "chapter1.txt",
			extension : ".txt",
			data      : [
				["Hello world", ""],         // [original, translation, ...]
				["Goodbye",  ""]
			]
		}
	},
	options    : { /* engine-specific, saved with the project */ }
}

common.initStaging(projectId?) creates the staging cache folder (<staging>/<id>/data) and returns {cacheID, cachePath}. Copy the game's files into cachePath + "/data" so the editor works on the staged copy — that is also where your exporter reads the originals from. This is exactly how the built-in custom parser module does it; its source (www/core/customParser/) is the reference implementation.

A complete minimal engine

The following addon adds an engine for plain .txt games: every line of every .txt file becomes a translatable row, and exporting writes the translated lines back.

// www/addons/txtEngine/package.json
{
	"name": "txt-engine",
	"title": "TXT Engine",
	"description": "Translate plain text files, one row per line.",
	"version": "1.0.0",
	"main": "main.js",
	"autoload": false,
	"load": ["main.js"]
}
// www/addons/txtEngine/main.js
const thisAddon = this;

engines.add("txt", { title: "TXT Engine" });

// Detection: recognize a folder that contains at least one .txt file
Engines.registerDetector(async (gamepath) => {
	let dir = common.isDir(gamepath) ? gamepath : nwPath.dirname(gamepath);
	let entries = await common.readDir(dir);
	let hasTxt = entries.some((p) => nwPath.extname(p).toLowerCase() == ".txt");
	return hasTxt ? "txt" : false;
});

// Creation: build the project object in JavaScript
engines.addHandler("txt", "createProject", async (args) => {
	const cache = await common.initStaging();
	const stageData = nwPath.join(cache.cachePath, "data");
	const files = {};

	for (const path of await common.readDir(args.gameFolder)) {
		if (nwPath.extname(path).toLowerCase() != ".txt") continue;
		const relPath = nwPath.relative(args.gameFolder, path).replaceAll("\\", "/");
		const content = await common.fileGetContents(path);
		const lines = content.split(/\r?\n/);

		const staged = nwPath.join(stageData, relPath);
		await common.mkDir(nwPath.dirname(staged));   // copyFile does not create parents
		await common.copyFile(path, staged);
		files[relPath] = {
			path: relPath,
			dirname: nwPath.dirname(relPath),
			basename: nwPath.basename(relPath),
			extension: ".txt",
			data: lines.map((line) => [line, ""])
		};
	}

	return {
		gameEngine: "txt",
		gameTitle: nwPath.basename(args.gameFolder),
		loc: args.gameFolder,
		projectId: cache.cacheID,
		parser: "txt-engine",
		cache: cache,
		files: files
	};
});

// Export: write translations back, then halt the default (PHP) exporter
engines.addHandler("txt", "exportHandler", async (targetPath, options) => {
	const saveData = trans.getSaveData();
	const stageData = nwPath.join(trans.project.cache.cachePath, "data");

	for (const relPath in saveData.project.files) {
		const file = saveData.project.files[relPath];
		const lines = file.data.map((row) => row[1] || row[0] || "");
		const target = nwPath.join(targetPath || stageData, relPath);
		await common.mkDir(nwPath.dirname(target));
		await common.filePutContents(target, lines.join("\n"), "utf8", false);
	}
	return true; // we handled the export ourselves
});

With this addon dropped into www/addons/ and the application restarted, picking a game folder in the New Project dialog detects the TXT Engine and Create project! runs entirely through the addon — no PHP, no core changes. Exporting works through the usual export entry points.

An engine addon can also add its own slide to the New Project dialog with ui.newProjectDialog.addMenu({...}) — the way the custom parser module does — for a tailored creation flow instead of the generic detected-engine path.

Shipping a documentation page

An addon can add a page to the offline documentation: it appears in its own Addons section of the sidebar, is covered by the documentation search, and is included in the index Ask DSLR answers from. Declaring it needs no code — just the optional docs field in package.json:

{
	"name": "my-addon",
	"title": "My Addon",
	"docs": "docs.html"        // one page, titled after the addon
}

Several pages use the array form:

	"docs": [
		{ "file": "docs.html", "title": "My Addon" },
		{ "file": "advanced.html", "title": "My Addon — Advanced", "keywords": "extra search terms" }
	]
  • Pages are HTML fragments like the built-in ones: start with a single <h1>, mark subsections with <h2 id="...">, no <html>/<body> wrapper. They are styled by the documentation's own stylesheet.
  • The page id is addon-<folder> (further pages addon-<folder>-2, -3, …), so a deep link looks like #addon-my-addon. The folder name becomes the id — keep it free of spaces.
  • Fragments are inserted into www/docs/index.html, so relative URLs inside a page resolve from there: reference a bundled image as ../addons/my-addon/img/picture.png.
  • Titles fall back per-page title → addon title → folder name; the addon description always feeds the search index.
  • A declared but missing page only shows the documentation's "could not load" notice — addon declarations never break the built-in pages, and deleting the addon folder removes its documentation with it.

Installing an addon

  • Addons are distributed as .tap packages (zip archives). Open the .tap file with SLR Translator — the application extracts it into www/addons/. Restart SLR Translator to load the new addon.
  • Alternatively, install by hand: copy the addon's folder (the one containing its package.json) into www/addons/ and restart.
  • To remove an addon, delete its folder from www/addons/ and restart.
Addon scripts run inside the application with the full access it has — its APIs and, through Node integration, the file system. Install only addons from sources you trust.

Reusing core-module libraries

Core modules keep reusable, dependency-free libraries in their lib/ folders (for example SEP's lib/game.js for RPG Maker collection/re-encryption, lib/crypt.js, or lib/ort_session.js for ONNX session handling). An addon may require() these by absolute path instead of bundling its own copy:

var path = require('path');
var sepDir = path.join(common.getRootDir(), 'www', 'core', 'SEP');
var game = require(path.join(sepDir, 'lib', 'game.js'));
  • Check before you rely on it. Probe the functions you need (typeof mod.collect === 'function') at addon start and show a clear message when the installed SLR Translator is too old, instead of failing mid-run.
  • One ONNX Runtime per process. If you need ONNX inference, use SEP's copy (www/core/SEP/node_modules/onnxruntime-node) and its lib/ort_session.js — loading a second copy of the native binding in the same process is unsafe. Session/GPU provider settings are shared per process: the first module to create a session decides the provider.
  • Never modify core files from an addon, and don't require anything outside the documented exports — internal functions can move between SLR Translator versions.

Writing your first addon

Create www/addons/myAddon/package.json with the manifest above (with autoload: true), and a main.js next to it:

const thisAddon = this;   // `this` is the Addon instance

// Wait for the editor, then extend it
$(document).ready(function () {
	ui.onReady(function () {
		// register an engine, add a toolbar button, hook the UI, ...
	});
});

The README.md inside www/addons/ documents the format and flags; the core modules in www/core/ are the best full-size examples — pick a small one (such as night mode) as a template.
