LLM & Online APIs

To be precise about what exists: SLR Translator v3 ships exactly two engines, SLR and DSLR. There is no separate roster of cloud engines. Online translation happens by pointing one of these two engines at a remote endpoint — in practice DSLR, since it speaks the OpenAI-compatible API format used by essentially every hosted LLM provider. SLR can likewise be pointed at Sugoi Translator servers hosted somewhere other than your machine (see Sugoi Translator).

Configuring a remote endpoint

Everything is set in Options → Translator & Language → DSLR (recommended) (details in DSLR Translator):

  • API URL — the provider's chat-completions path. A URL entered without a scheme is treated as a secure connection automatically; a missing v1/chat/completions suffix is appended for you. Endpoints ending in /responses are also supported.
  • API Key — the provider key, one per endpoint (the fallback model and the glossary extractor each have their own key field).
  • Model — the provider's model identifier, exactly as the provider documents it. No specific model is recommended; model names and what is good change constantly.

The built-in Options Preset 1 is an example of a hosted setup: it points DSLR and the glossary extractor at the Nano-GPT aggregator. The model name inside it is a placeholder from the time it was written — replace it with whatever that provider currently offers before applying. Other providers named in the engine's own option texts include OpenRouter and the official DeepSeek API (which supports the simpler json_object response format instead of full JSON schemas); Gemini's native API is supported for reasoning configuration. Any provider with an OpenAI-compatible endpoint works the same way.

Keys and secrets

  • Keys are stored in plain text in the application's local configuration — the option descriptions say so explicitly. Do not share your configuration or preset JSON with keys embedded.
  • Multiple keys for the same provider can be entered as parallel endpoints with individual weights, and Group Endpoints by URL rotates across keys of one provider when it rate-limits globally instead of per key.
  • A rate-limited endpoint (status 429) backs off with an escalating cooldown from 10 seconds to 30 minutes; an endpoint returning 401/403/404 (bad key, bad address, no permission) is skipped for the rest of the running job instead of being retried forever.
  • For free-tier models, the fallback Request Delay option text recommends at least 3000 ms between requests.

Cost and usage monitoring

  • After a batch run, the progress log prints total token usage (prompt, completion, total) for the run, plus a quality summary (batch splits, fallback activations, retries, rate-limit events and failed translations).
  • Caching reduces cost: session batch cache by default, and the optional persistent caches across sessions. Remember that context prompts, scene context and an active glossary disable the Clean Cache (entries produced with them are not reusable out of context).

Privacy

With a remote endpoint, your game's text — and, when enabled, scene context and the generated glossary — is sent to the provider you configured, and translated text comes back. Everything else (parsing, editing, caching, applying translations to the game) happens locally. If that matters for your project, run DSLR against a local server instead: the same engine, fully offline. See Overview & Requirements for the offline-first picture.

Choosing a provider

  • Local, private, free after hardware: a local OpenAI-compatible server (LM Studio is the default endpoint; other local servers in OpenAI-compatible mode work too). Details and model guidance in DSLR Translator.
  • Hosted, no local GPU needed: any aggregator or first-party API with an OpenAI-compatible chat endpoint. The engine's option texts name Nano-GPT, OpenRouter and DeepSeek as examples of such endpoints.
  • Mixed: a fast cheap hosted model as primary and a stronger one as fallback, or several keys of the same provider pooled as parallel endpoints.
