DSLR Translator

DSLR is the LLM translation engine. It sends text to any endpoint that speaks the OpenAI chat-completions format (or the newer /responses format), local or online, and comes with a large toolbox around it: editable prompts, batch modes with validation and retries, a fallback model, context and scene awareness, glossary injection and several cache layers.

Endpoint setup

Open Options → Translator & Language → DSLR (recommended). The Quick Start box at the top holds the three fields a normal setup needs — API URL, API Key and Model — with a Test connection button that sends a one-token request and reports the result. The rest of the form is optional; the power-user sections sit under an Advanced heading near the bottom.

OptionDefaultMeaning
API URL 127.0.0.1:1234/v1/chat/completions The endpoint address. The default matches a local LM Studio server; any other server exposing an OpenAI-compatible API works too (other local inference servers such as KoboldCPP or Ollama in OpenAI-compatible mode, or hosted providers — see LLM & Online APIs).
Do not attempt to fix URL off By default the engine adjusts the URL: a missing v1/chat/completions suffix is appended automatically, and a URL that already ends in /responses is used as-is. Enable this to send requests to exactly what you typed.
API Key empty Leave blank for most local servers. Required by hosted providers. Stored in plain text in the application configuration.
Model qwen35-4b-paperwitch-q8.gguf The model name your endpoint expects. The default matches the optional example package of the bundled local runtime; if you use a different endpoint or model, change it to whatever your provider offers.
There is no separate model-template screen in v3, and no built-in model recommendations — use whatever model your provider offers. Per-model flags go into chat_template_kwargs (for example Qwen's enable_thinking), and reusable whole-engine configurations are saved as Options Preset JSON slots.

Parallel endpoints and fallback

  • + Add Endpoint at the end of the Connection & Model section adds another endpoint card. Each endpoint has its own URL, key, model and settings, plus a Weight (how many batches it may handle at once — total concurrency is the sum of all weights). Endpoints with a blank URL are skipped. A new endpoint starts as a copy of Endpoint 1's current settings (except URL and key, which stay blank) so similar endpoints need no re-entry; afterwards each endpoint keeps its own values and never follows Endpoint 1 — if you want more of the same backend, raise Endpoint 1's Weight instead.
  • Option groups whose API URL is blank — Fallback, Glossary, Review and extra endpoints — render dimmed with an (inactive) note, since their values currently do nothing. Fill the URL and the group activates immediately; the fields stay editable while dimmed.
  • Group Endpoints by URL makes endpoints sharing one URL share a single concurrency pool with key rotation — for providers that rate-limit per IP rather than per key. URL-Group Rotation Delay spaces out retries between keys of the same group.
  • Independently of parallel endpoints, a Fallback model (second URL/key/model plus its own copies of most settings) can take over when the primary model gets stuck. The fallback is disabled until you turn on Enable Fallback LLM (it is off by default); once enabled and the fallback URL is filled in, it is tried on the same failed batch before the batch is split, so no context is lost. Limit Fallback to Single Requests restricts the fallback to retrying individual lines instead of whole batches, which suits slow local models.
  • Rate-limited endpoints (status 429) get an escalating cooldown from 10 seconds up to 30 minutes; endpoints returning 401/403/404 are treated as misconfigured and skipped for the rest of the job. An endpoint that keeps failing to answer at the transport level (timeouts, connection errors, 408/5xx) is put on the same escalating cooldown once a review call has spent its network attempts, so the next review row rotates to another endpoint — or fails closed for that row — instead of repeating the same error loop. A single successful request clears the cooldown.

Prompts

Every prompt DSLR sends is editable in the Prompts section (large text fields). The main ones:

Full Batch translation

  • Enable Full Batch Translation (default on) packs many rows into one request — much faster and cheaper, but the model must be able to follow the batch format.
  • Enable JSON Full Batch Translation (default on) sends the batch as JSON and demands a JSON schema response. Limit JSON Full Batch to json_object Response Format is for providers that support the simpler json_object mode instead of full schemas (the option text names the official DeepSeek API as an example).
  • Batch sizes are governed by the Batching & Limits options (Maximum Scene Size, Target Request Size, Scene Threshold, scene/row caps), which also drive the scene-aware packing described in Batch Translation.

Retry and quality control

  • Enable Retry (default on): rejected responses are retried up to 12 times with correction prompts containing the error details; a failing Full Batch is retried twice, then handed to the fallback model, then progressively split in half down to line-by-line.
  • Enable Automatic Reject and Enable Automatic Reject of Japanese validate responses (format rules, leftover Japanese) before accepting them.
  • Reject Missing Glossary Terms (default on) validates each translation against the project glossary with no model call, so it works even with Review (QC/judge) off. When the source line contains a glossary term that has a translation, the English must reflect it: the term itself, or — for character and name entries — a matching pronoun (he/him/his/himself, she/her/hers/herself, they/them/their/theirs/themselves) or gendered word (man/guy/father/brother…, woman/lady/mother/sister…). A line that drops or renames the term (for example Aida translated as Ada) is rejected and retried with the missing terms listed. If a different rendering is genuinely correct, the retry prompt lets the model authorize it by appending GLOSSARYDIFF at the end of its response (the token is stripped before saving). Matching is stem-based, so an inflected form of the term (brainwashed for Brainwashing, transformed for Transformation) still counts. Entries of type unknown, entries without a translation, and entries whose translation offers alternatives or reads as a definition (e.g. Charm/talisman) are never enforced, and terms are matched longest-first so a compound term is not shadowed by a shorter one. This is a presence check, not a correctness check; disable it if the glossary holds terms that are commonly rendered with valid synonyms.
  • Enable Removal of Repeating Japanese trims characters repeated 5+ times in a row — runaway repetition can send small models into token-spam loops.
  • The four Repetition Loop Threshold options catch those loops while they happen: while a response streams, the engine watches for the model repeating itself and terminates the response early instead of letting it generate on until the token limit. Each tier is settable independently and disabled with 0: (Single Characters) (default 20) covers drawn-out sounds like “Ahhhhhhhh” or long punctuation runs, (Words & Sentences) (default 15) covers repeated words, phrases and sound effects like “Ah Ah Ah Ah”, (Entries) (default 4) covers structured content that can never legitimately repeat — glossary term definitions, batch sections, whole blocks of distinct entries cycled as a group, and duplicated response ids (--- {дivN} --- markers or JSON entry ids; every id exists exactly once in the original, so any repetition is duplication, and the id check also fires on ids beyond the batch's range) — and (Repeated Content) (default 6) covers a derailed reviewer working through the same material over and over: the same line re-issued verbatim (“Let's check @6 again… is the issue” many times) or one row revisited again and again with slightly different wording. Unlike the other tiers it counts repeats across the whole response, not just back-to-back copies, and row numbers stay part of the comparison — so a QC pass reporting the same defect class for many different rows is normal output and never counted as a loop. A kill names the repeated line or revisited row in the log and the content generated before the kill is logged to the console, so a fast termination stays diagnosable. When a tier trips, the request is retried exactly like a “length” finish reason — the retry automatically increases repeat_penalty / repetition_penalty / frequency_penalty, whichever is set — but it logs as a repetition loop with the exact cause (e.g. “section marker id 1 appeared 4 times”), so it stays distinguishable from a genuine token shortage. Requires streaming to be active (Enable Token Progress Display on and Disable Stream off), because the repetition has to be watched while the response is generated; the thresholds apply to translations, glossary extraction, and review (QC/judge) alike — except (Repeated Content), which currently watches review streams only — and raising them helps projects whose text legitimately repeats a lot.
  • Request Delay (default 50 ms) spaces requests; retries add 1 s (bad response), 3 s (rate limit) or 30 s (unknown server error).

The quality-control toggles — Enable Retry, Enable Automatic Reject, Enable Automatic Reject of Japanese, Reject Missing Glossary Terms, Enable Removal of Repeating Japanese and Enable Removal Inner IDSP Characters — are set once and shared by every endpoint in the pool: additional endpoints (2, 3, …) have no copies of their own and always use Endpoint 1's values. The Fallback model is the exception — it has its own set in the Fallback card, so a fallback can retry, reject, or clean up source text differently from the primary.

Review Translations and Auto-Fix

DSLR can ask the model to re-read its own translations and flag the suspect ones for you. Three toggles control this, all in Options → Translator & Language → DSLR (recommended), section Retry and quality control; Review Translations and Auto-Fix Flagged Translations are off by default and Judge QC Findings is on by default.

  • Review Translations (tag suspicions medium purple) — after each batch the source/target pairs are sent back to the model, which reports defects as findings; every row a finding cites is tagged mediumpurple (medium purple). The semantic review's tag is separate from the built-in purple heuristics (the length-ratio and structural checks that flag unusually short or long translations): both run independently, so a row can carry purple, mediumpurple, both, or neither. Medium purple only ever comes from the review, and only the review clears it.
  • Auto-Fix Flagged Translations — has no effect unless Review Translations is on. Every flagged row is judged: the finding is either dismissed or confirmed as redo. A confirmed row is rejected inside the normal single-line checks and retried by the same retry mechanism as any other rejection (up to the engine's per-line retry limit), with the judge's reason added to the retry prompt; it is re-reviewed after each attempt with the surrounding batch lines as context, but the re-check judges only that row — neighboring rows are context, never verdict targets, so only its own fix can trigger another retry. Neighbors already accepted in the run contribute their final text; rows still carrying a pending redo are shown source-only, since their wording is about to change and must not serve as ground truth. Medium purple follows the review outcome: a dismissed row loses it, a re-reviewed clean row loses it, and a row keeps it while the judge confirms a problem or the review could not decide (malformed verdict, failed call) — those stay for manual review. A row where every finding was dismissed leaves the run untagged. A row that is still confirmed after Review Retry Rounds exhausts keeps its medium purple even though a translation was accepted — the best-reviewed of the original and its retries is kept (clean beats flagged-without-redo beats redo, redo ordered by severity, earliest wins ties — so the original survives when nothing beat it), and that translation passed all absolute checks, but the reviewer still suspects it.

Judge QC Findings (same section, on by default) controls whether QC findings are adjudicated before anything is done with them. On, each finding is judged and only a confirmed redo orders a retranslation, so QC false positives are filtered out. Off, every finding at or above Review Minimum Severity orders the retranslation directly and the judge call is skipped entirely — the Review: Judge prompts are unused and the [DSLRReview] judge … log lines no longer appear. This is faster and cheaper, and is meant for setups where the Review model is the same as the translation model (a same-model “second look” adds little), but every QC false positive then costs a retranslation and a re-review instead of being dismissed. Leave it on when the Review endpoint points at a separate, stronger model, where the adjudication earns its keep.

Two further options tune this, in the same Retry and quality control section: Review Retry Rounds (default 5, 0–10) — how many times a confirmed row may be retranslated and re-reviewed before it is left medium purple (0 = flag only, never retranslate); and Review Minimum Severity (default Low) — findings below it still tag the row medium purple but never trigger a retranslation. Re-reviews raise the bar progressively: the first re-review of a retried row judges at Review Minimum Severity, then each further round one rank higher (Low→Medium→High, capped at High), so a style nit that ordered one retry cannot order the next by itself and the bar tightens as a row burns attempts — only a genuinely worse finding re-triggers. Disable Escalate Minimum Severity on Re-Review (same section, on by default) to re-review every round at Review Minimum Severity instead. Each review request keeps two separate retry budgets: network/transport failures get 3 tries with the escalating backoff, while a response caught repeating itself gets 5 tries (flat 5-second wait with a small repetition-penalty bump each time), so a model that can escape a loop has the room to, without stretching a dead endpoint's backoff.

Four loop guards keep weak models from burning retries on their own suggestions. QC findings must describe the defect only and never propose replacement wording, and the judge's reason must state a requirement rather than a replacement phrase — a quoted suggestion would otherwise be copied into the retranslation order verbatim, ordering a fix one round and condemning it the next. Every re-review is shown the row's prior attempts and the ruling each drew, so it judges the fix against what was already tried. A retranslation identical to the already-reviewed text is accepted as-is with its flag kept and no further calls (logged as no progress). A re-review that repeats the previous round's ruling — same category, same substance in different words — ends the loop early the same way (logged as same complaint), since the model has shown it cannot fix that row. And when rounds exhaust, the best-reviewed attempt is kept instead of whatever the last retry produced (see above).

Review becomes active for any DSLR translation run — Batch Translation (both Full Batch and line-by-line batch runs record the escaped “wire” source/target pairs the review needs) and single-line editor translations, which update a row's medium purple the same way. Rows the engine could not pair — for example rows carrying failure markers such as SHISAYE. — are left alone rather than guessed at.

Review runs in a fixed order with the absolute checks. Rows the batch validation already flagged — leftover-Japanese and missing-quote rows it tolerated within its thresholds — skip the seed review (logged as skipping seed review) and go through the single-line structural pass first; their fixed text is re-reviewed on the first structurally-clean attempt instead, so QC never re-reports problems the validator already knows about. Every attempt, including review-fix retries, re-runs the structural checks before any review verdict, so a problem a fix reintroduces is caught the same way.

Find the flagged rows with Find → Target: Tag → mediumpurple; the search locates every medium-purple row so you can inspect it by hand (the legacy purple tag is searched the same way and keeps its own meaning — see Cell Color Tags). The review can never block or corrupt a batch: a QC, judge or retry call that fails is logged and degrades to “no flag” / “no retranslation”, leaving the translation and its tags untouched — worst case a row stays medium purple for manual handling. Review decisions are logged — each finding ([DSLRReview] finding @123 [high/mistranslation] …) and each judge verdict ([DSLRReview] judge @123: redo — …) — in both the in-app log and the console (F12).

The translation-quality summary also reports what the review cost, as a [DSLR] Review (QC/judge): N calls · prompt X · completion Y tokens line (review calls are otherwise separate from the translation token totals).

The review never replaces the normal checks — they are absolute. Once a batch has passed the full-batch validation, the reviewer runs inside the normal single-line processing and acts as one more line check: a confirmed row is rejected with the judge's reason exactly like a placeholder or length failure, so the existing retry mechanism re-translates it (bounded by the engine's per-line retry limit) and the retry flows through every other line check, re-reviewed after each attempt up to Review Retry Rounds. The reviewer never writes translation text, so the escaped parts (@n placeholders) and every other pipeline step are handled by the normal path. Medium purple reflects the latest review outcome: it is set while a row is flagged and cleared when that row's review comes back clean — a dismissed finding, or an accepted retry that re-reviews clean.

The four prompts the review uses — Review: QC System/User Prompt and Review: Judge System/User Prompt — are editable in Prompts → Review. They use the same escaped placeholder form as the translation prompts ([[ROWS]], [[FINDING]] and [[CONTEXT]] are replaced per call). The default system prompts tell the model to keep every placeholder token byte-identical while still reading each for what it stands for: character-name tokens ({PERSONn}, always a name) are judged for pronouns, honorifics and agreement, nameplate tokens ({NAMEn}) label the speaker, variable tokens ({Vn}) usually hold a number, and image/color/escaped tokens are pure codes. In-text line breaks inside a reviewed row are shown to the model as ⏎. The prompt asks QC for short notes, but the hard cutoff is generous (1000 characters, cut at a word boundary — never mid-word), so a thorough finding always reaches the judge whole instead of arriving as a cut-off fragment. QC is told to skip pure quote/bracket-balance findings — quote and placeholder balance is enforced by absolute checks and a repair pass, and the judge is told to dismiss such findings — so rows are not flagged or retried for counts the pipeline already handles; only a quote problem that changes meaning or attribution is review business.

Both the batch review and every re-review also receive the same glossary and scene context the translation requests get (filtered on the batch source), rendered into [[CONTEXT]] at the top of the QC and judge messages — so the reviewer knows the project's terms and the scene's setting, e.g. which world a scene takes place in. If a customized user template drops the [[CONTEXT]] marker, the context is appended to the message instead of being lost silently. With KV-Cache Friendly Prompts on, the context instead travels as a separate user message ahead of the review task — mirroring the translation requests, so the review's system message stays stable and cacheable. When Review Context Length Limit is set, these sections are trimmed to fit (scene first, then glossary); the rows under review are always sent whole.

Review endpoint, model and sampling

QC and Judge can run on a different endpoint and model than the translation itself — useful when you want a stronger or uncensored model to judge the output, or to spread review calls across a second server. The Review fields mirror the Glossary Extraction ones and live in Connection & Model → Review, Sampling & Generation → Review and Batching & Limits → Review: Review API URL, Review API Key, Review Model, Review Do not attempt to fix URL, Review temperature, Review Request Delay, Review top_k/top_p/min_p, the repeat/repetition/frequency/presence penalties, Review chat_template_kwargs, Review Custom Headers, Review Custom Parameters, Review Reasoning Format/Review Reasoning Effort/Review Reasoning Budget, Review max_tokens Parameter, Review Context Length Limit, and the three streaming display toggles below.

Review max_tokens Parameter is the ceiling for review responses and is scaled down by input size, mirroring translation: seed reviews (the whole batch under review) scale like full-batch requests (characters × 1.5, never below 1000 tokens) and re-review retries (a single row under verdict) scale like single-line requests (characters × 3.5, never below 500 tokens). There is intentionally no separate absolute cap for review — one ceiling plus the input scaling is the whole story.

Review endpoint selection is all-or-nothing and driven by the Review API URL. While the Review API URL is blank, Review (QC/Judge/Fix) uses the endpoint that translated those rows with all of its options, and every Review connection/sampling/limits/display field is ignored. Once a Review API URL is set, ONLY the Review fields are used — a blank Review field is sent as blank (parameters that must stay empty to be omitted are not sent, toggles stay at their Review value) and nothing is copied from the translation endpoint. There is intentionally no per-option fallback: mixing the two option sets field-by-field would be confusing and would break toggles and empty-means-unsent parameters. The JSON-schema/JSON-object response-format options from Glossary are intentionally not mirrored — review responses use text contracts.

Like the translation and glossary paths, every Review call shows a live [DSLRReview] Generating review response: N tokens counter in the loading console while it generates (labelled QC or judge), with the streamed response text previewed above it; both disappear when the call completes so the log does not grow. The three toggles live in Sampling & Generation → Review: Review Disable Stream forces non-streaming calls (the old behaviour — use it if your provider rejects streaming requests), Review Enable Token Progress Display drives the counter and the streaming behind it, and Review Enable Stream Preview Display controls just the preview. As elsewhere, the full request and the full response of every Review call are logged to the F12 console (never the API key), alongside the in-app verdict lines.

Review calls share the translation endpoint's transport behaviour. A 429/524 registers that endpoint's cooldown (shared with the translation dispatcher) and review moves to a spare configured endpoint when one is available before retrying; a 401/403/404 means a bad key, URL or permission, so the endpoint is disabled for the rest of the job and the call fails immediately without retrying. Other errors retry up to three attempts with 3s/9s (rate limit), 10s/20s (HTTP 400) or 30s/90s (other) backoff. A review call that ultimately fails is logged and treated as “no flag”/“no retranslation”, so the batch never stops.

Streamed review responses share the translation path's repetition-loop guard: while generating, the engine watches for the model repeating itself (character and word tiers — review responses carry no structured entries, so the entries tier does not apply) and terminates a looping response early instead of letting it run to the token limit. The call is retried with an increased repeat_penalty / repetition_penalty / frequency_penalty (whichever is set), like the translation path. Loop output is never adjudicated — a call that is still looping when attempts run out fails closed (flags kept, row unreviewed) rather than turning model garbage into findings. Like translations, this requires streaming to be active.

Thinking / reasoning control

  • Reasoning Format is the single switch for all of this — the older Disable v4 thinking, Always Send Disable Thinking Parameter and Qwen enable_thinking Auto-Control options have been removed, because each of them only did part of what one selection now does. It has two "off" choices:
    • None (default) — disabled. The app turns thinking off using whatever disable parameter the endpoint actually understands: DeepSeek hosts get thinking { type: "disabled" }; /v4/ and /responses URLs get that plus reasoning_effort "none", which is what Ollama's OpenAI-compatible endpoint needs (it ignores the thinking object entirely); the bundled local runtime and Qwen-named models get chat_template_kwargs.enable_thinking = false, and a Qwen model additionally gets the /no_think soft switch appended, which works even on a server that ignores the parameter. That last part is what makes a model which thinks by default — Gemma 4 is one — stop without any extra setting.
    • Not enabled — hands-off. Nothing is sent: no reasoning is asked for, and no disable parameter is sent either. Choose this when a provider rejects fields it does not recognise and you want the request left completely alone.
    Where the app cannot tell what an endpoint accepts — a plain cloud chat/completions URL that is not DeepSeek, /v4/, /responses, local or Qwen-named — None sends nothing rather than inventing a field, so a working request can never start failing because of it. If you need a specific provider's disable field on such an endpoint, add it through Custom Parameters.
  • Both "off" choices are inactive as far as reasoning is concerned; the difference is only whether a disable parameter goes out. Neither is sent while a reasoning format is active, so enabling reasoning still works.
  • Reasoning Format can explicitly enable reasoning for models that benefit from it: OpenAI-style reasoning_effort (also the only format Ollama's OpenAI-compatible endpoint honors), an OpenAI-compatible thinking object with a token budget, Gemini's thinkingConfig, or Qwen's enable_thinking — each with an effort level (up to max) and optional explicit budget. Enable Reasoning (legacy) covers old models that always dump their think block into the response.
  • Reasoning traces returned by the model are captured from both reasoning_content (DeepSeek-style) and reasoning (Ollama-style), shown live in the token-progress preview, and kept out of the translation output.

Context

  • Enable Context Messages (default on) includes the last translations as context; Context History Length (default 8) sets how many.
  • Scene Context (default on) appends scene information from the Scene Graph (dialogue flow, speakers, cross-file Common Event links) for RPG Maker projects.
  • Each part has its own context budget, all 0 = off: Context Length Limit (Endpoint 1 / main), Fallback Context Length Limit, Glossary Context Length Limit and Review Context Length Limit — extra pool endpoints each carry their own copy too. A part whose API URL is blank uses the main limit instead. When set, the engine estimates the token cost of the system prompt + user text + response reserve and trims the auxiliary context to fit: scene first, then glossary for translation requests; the already-collected-terms context for glossary extraction (the text chunk under extraction is never trimmed); the glossary/scene sections for review requests (the rows under review are never trimmed) — so weak models do not run out of context window.
  • KV-Cache Friendly Prompts (stable system prompt) (default on) restructures the requests for prefix/KV-cache servers such as SGLang (radix cache), vLLM automatic prefix caching, LM Studio or llama.cpp. Normally the system prompt is assembled from the base prompt plus everything that can change between requests — the System Prompt Addition, the glossary, Scene Context and the previous-translations context — so every batch gets a different system prompt and the server's prompt cache misses every time. With this option on, the system message contains only the constant translation rules (the base System/Batch System Prompt) and is byte-identical for every request, while all variable context moves into a separate user message sent right before the actual translation request. The model receives the same information in the same relative order, so translations are unaffected — only the message layout changes, and cached prompts are reused instead of re-processed on every request. The option applies to the primary model, the fallback model, Full Batch and line-by-line requests alike; Context Length Limit budgeting keeps working unchanged. Review (QC/judge) requests follow the same layout when the option is on: their glossary/scene context travels as a separate user message ahead of the review task instead of inside it.
  • Name Placeholder Genders maps RPG Maker actor IDs to genders so pronoun substitution in \N[] placeholders can be validated.
  • Glossary injection is configured here too — see Glossary Extractor.

Sampling and request options

All sampling parameters are optional — leave a field empty and it is not sent. Defaults: temperature 0.0, repeat_penalty 1.05 (an LM Studio style parameter the option text warns is unsupported elsewhere — clear it for non-LM Studio endpoints), everything else (top_k, top_p, min_p, repetition_penalty, frequency_penalty, presence_penalty) empty. Max Response Tokens (default 5000) is auto-scaled down to the input size. Custom Headers and Custom Parameters accept JSON objects merged into every request. Enable Token Progress Display streams a live token counter while the model generates. Enable Stream Preview Display (default on) additionally shows a live preview of the streaming response, only while the response is still generating; the token counter sits below the preview so it stays in view while the preview grows. When several responses stream at once (endpoint pool concurrency), the previews are hidden by default and only every stream's token counter keeps updating; Stream All Concurrent Responses shows every stream's live preview at the same time instead — meant for setups with few but very slow connections. Turn the preview off to keep just the token counters. The full request/response logging stays in the F12 devtools console either way. The four Repetition Loop Threshold options also live in this section — see Retry and quality control.

Placeholder handling

RPG Maker control codes are replaced with LLM-friendly tokens before sending and restored afterwards. Defaults: \n[1] → {PERSON1}, \nw[1] → {NAME1}, \i[1] → {I1}, \v[1] → {V1}, \C[1] → {C1}, escaped fragments @1 → {%1}. Each mapping is editable in the Placeholders section, along with the placeholder symbol style (Placeholder Type), recovery behavior for lost placeholders (Placeholder Recovery type, default Guess) and Replace \n with <br>. The Text Processing and Patterns sections expose the sentence-splitting engine (processing order, protected/splitting/isolation patterns) for unusual games.

Caching

  • Batch Cache (default on) remembers exact batch results within the session; Line Cache remembers single sentences at the cost of context (overrides Batch Cache).
  • Persistent Cache survives restarts for the configured model. Clean Persistent Cache only records translations produced without project-specific context (no Context Prompt, scene context or glossary), so those entries stay reusable across projects. Both write JSON files named after the engine and model (for example CleanCacheDSLR_<model>.json) into the engine module folder; Persistent Cache Size caps their size.
  • Changing prompts, placeholder tokens or the /no_think behavior invalidates existing Clean Cache entries; the option texts recommend resetting the cache file when that happens.
