SEP Picture Translation

SEP turns pictures into a translation project. It scans image files with on-device OCR, turns every detected text box into a normal translatable row, and — when you export or inject — erases the original text on each image and draws your translation back onto it. Everything runs offline: the OCR models, the inpainting networks and the drawing font are bundled with the application, so there is nothing to install and no Python involved.

Typical uses are pictures with Japanese text (title screens, UI graphics, CGs) and whole RPG Maker games whose story is told through images instead of script files.

Requirements

  • No setup: SEP ships its own models — a PP-OCRv6 detection and recognition model pair (ONNX Runtime), an AOT inpainting network (about 22 MB) and a LaMa inpainting network (about 200 MB) for text removal, plus a Unicode-capable TrueType font for drawing.
  • The first project start loads the OCR models, which takes a moment; they stay loaded afterwards.
  • OCR and inpainting run on the GPU when a usable one is found, using execution providers that are already bundled with SEP (WebGPU, with DirectML as a Windows fallback) — nothing extra to install and no vendor SDK required. When no GPU is available, SEP falls back to the CPU automatically. GPU acceleration is on by default and can be turned off under the SEP options.
  • OCR over a whole game's picture folder can take a long time — prefer the staged workflow described below for large games.

Starting a project

Open New Project and pick the SEP slide. Select a folder — what happens next depends on the folder:

Folder typeBehavior
Plain image folder The images (PNG, JPG/JPEG, BMP, WebP, TGA, PCX) directly in the folder are listed and OCR'd on Start project. Subfolders are not scanned.
RPG Maker game folder (XP/VX/VX Ace, MV, MZ) The folder is scanned recursively. Encrypted MV/MZ images are decrypted automatically. Start project collects every image into a staging folder next to the game (<game>_sep) and runs OCR on all of them — the dialog itself warns this can take ages on large games.
Packed RGSS archive (Game.rgss3a etc.) Images are extracted from the archive before OCR. Export writes the decrypted folder structure — SEP cannot re-pack the archive, so the game needs the extracted files instead.
SEP staging folder (created by Collect only) OCR runs only on the images still present; images you deleted from the staging folder are ignored.

The staged workflow (recommended for games)

  1. Select the game folder in the SEP slide and press Collect only. All images (encrypted ones decrypted) are copied into the staging folder <game>_sep next to the game, keeping the game's folder structure. Encrypted videos (.rwebm files, as produced by third-party "webmplay"-style video plugins) are collected as well, decrypted to plain .webm for manual editing. You can close SLR Translator at this point.
  2. Open the staging folder and delete every image that contains no translatable text — logos, textures, system graphics. This is the step that keeps the OCR run short. Videos are never OCR'd; keep them in the staging folder if you want to work on them.
  3. Start a SEP project on the staging folder: Start project OCRs exactly the images that remain.
Manually edited images (for example pictures you retouched in an image editor) can be pushed back into the game without any project: select the staging folder in the SEP slide and use Encrypt only to re-encrypt the images still present into a folder of your choice — the game folder, for instance. This also covers images with no detected text that the project filters skipped, and re-encrypts collected videos back into their original .rwebm files. Video translation itself is manual: replace or edit the decrypted .webm files in the staging folder (subtitles, re-encoded video, …), then use Encrypt only.
If a collection run was interrupted for an MV/MZ game, the encryption information may be missing. SEP warns about this in the slide: re-collect the game folder (or run Collect only again) before exporting, otherwise the exported images will be plain PNGs the game cannot load. See Encrypted & Packed Games for background.

The OCR stage

  • Every detected text box becomes one row. The row's context shows the image path, the box id and the OCR recognition score.
  • Select a row and switch to the Raw tab in the cell info panel: SEP shows the source image with the detected text region highlighted in red, together with its OCR score — handy for judging whether a low-confidence box needs manual fixing.
  • Vertical Japanese text (tategaki columns) is recognized twice — once horizontally and once in the vertical orientation — and the higher-confidence result is kept. Horizontal text is only ever recognized once.
  • Boxes below the OCR score threshold (default 0.5) are discarded.
  • Project filters, applied when the project is created: Discard images without detected text (on by default) drops images with no text at all, and Discard images without Japanese text (off by default) drops images whose text contains no kanji/kana — useful to skip logo-only images.

Translating

From here on a SEP project behaves like any other: fill the translation column by hand, use Context Translation, or send everything through an engine with Batch Translation. The color tags described in Cell Color Tags apply as usual.

Boxes whose translation matches the original OCR text (ignoring full-width/half-width forms, letter case, whitespace and punctuation) are left untouched on export — the already-correct original is not erased and not redrawn. Append d{} to a row's translation to force a redraw anyway.

Export and inject

On export (to a folder or a zip) or injection, SEP renders every image: the original text is erased, the translation is drawn into the same region, and the file is written back in its original format.

  • Text removal method: none (draw over the original), blur (fast, good on plain backgrounds), AOT Inpaint (compact neural network) or LaMa Inpaint (larger model, 512×512 crops per region — the default and usually the best reconstruction on textured backgrounds).
  • Solid-color backgrounds are detected automatically and filled with the exact background color instead of being blurred/inpainted — clean fills on flat UI panels without color casts.
  • The translation is drawn with a bundled condensed Unicode font by default; any TrueType font placed in the SEP module folder can be selected as Render font. Font size is auto-fitted per box (grouped so a text block shares one size) with a configurable Minimum font size floor.
  • Match original text color detects the dominant color of the original text and reuses it; an automatic outline is added when the text would otherwise be hard to read against the new background (always on transparent images).
  • JPEGs are re-encoded at the estimated original quality with EXIF data preserved; BMP, TGA, PCX and WebP files are written back in their original format.
  • Encrypted game images are re-encrypted into their original files (e.g. img/system/Window.rpgmvp), and a viewable PNG copy is written under decrypted/ mirroring the game's structure so you can check the result without launching the game.

Per-row overrides

Override tokens can be appended to a row's translated text; they stack with each other:

TokenEffect
r{none} / r{blur} / r{aot} / r{lama}Text removal method for this box only.
f{18}Force the font size in pixels for this box.
c{255,0,0} or c{white}Force the text color for this box.
d{}Erase and redraw even when the translation matches the original.

SEP options

All SEP settings live in the Options dialog under the SEP tab: removal method and inpainting parameters, OCR thresholds and filters, vertical-text handling, angle snapping, font size grouping, blur strength, solid-background detection, text color matching and GPU acceleration. GPU acceleration is experimental: it uses the GPU through ONNX Runtime's WebGPU provider (DirectML is tried as a Windows fallback) and falls back to CPU automatically when no usable GPU is found. If you suspect GPU-related problems or incorrect results, turn it off to force CPU. Changing the render font, the outline thickness or GPU acceleration requires a restart; the project filters take effect the next time a project is created.

Limitations

  • OCR quality decides row quality: misread text must be corrected by hand, and a bad box outline (extravagant fonts, flourishes) can leave artifacts — the auto-grow fill option mitigates this on solid backgrounds.
  • Videos are not OCR'd or otherwise translated automatically. .rwebm files are collected decrypted (as .webm) and re-encrypted by Encrypt only; translating their content is a manual step. Only the known third-party video encryption scheme(s) are supported — if the videos of a game use an unknown scheme, they are left in place and a message is logged.
  • Packed RGSS archives cannot be re-packed; export produces the decrypted folder structure.
  • Re-encryption needs complete collection information; interrupted collections must be re-run (see the note above).
  • The intermediate OCR box JSONs are project-internal data and never appear in exports.
