Escape & Text Codes

RPG Maker games do not display message text verbatim. The engine interprets control codes — short sequences starting with a backslash, like \C[2] for a text color or \n[1] for an actor's name — and replaces them with colors, icons, variable values and names while the game runs. RGSS-based engines (XP/VX/VX Ace) additionally use C-style format tokens such as %s and %d inside scripts, which the game fills with values at runtime.

These codes must reach the game exactly as the developer wrote them. A translation that drops a %s, swaps %s with %d, or leaves a stray backslash can crash the game or garble its text. SLR Translator therefore recognizes these codes, hides them from the translator while preserving them, and checks after every translation that they survived — anything suspicious is flagged with an error code.

Common MV and MZ codes

The codes below are the ones SLR Translator handles explicitly — they are replaced with safe placeholder tokens before the text is sent to a DSLR translation model, and restored afterwards. n stands for a number.

CodeWhat the game does with itToken sent to the model
\n[n] / \N[n]Shows actor n's name{PERSONn}
\nw[n] / \NW[n]Shows character n's name (name-window plugins){NAMEn}
\i[n] / \I[n]Shows icon n{In}
\v[n] / \V[n]Shows the value of variable n{Vn}
\C[n] / \c[n]Changes the text color to n{Cn}
@nProtected numeric placeholder used by the translation pipeline{%n}

Other codes are passed through untouched, for example:

  • \G — the currency unit.
  • \! — waits for a key press; \. — short pause. During the batch fix-up pass these two are protected internally so their backslash cannot be eaten by surrounding fixes.
  • %1, %2… — choice-window placeholders that MV/MZ fills with the selected entry's number.
  • Plain newlines inside a cell are the message's line breaks; plugins that use \n-style line breaks are handled as literal text sequences.
Plugins add their own codes on top of the engine's built-ins (\fs[n] font size, \p[n], \M[n], \VS[…], \NA[…], picture-name codes like \picn[…] and many more). SLR Translator's checks are aware of a long list of these, but a game with unusual plugin codes can still produce UNKNOWNCOMMAND flags — treat them as “check this cell”, not as a certain error.

Common RGSS codes (XP / VX / VX Ace)

RGSS games keep most translatable text inside Ruby scripts, so the tokens that matter are format specifiers and script placeholders:

TokenWhat the game does with it
%sFilled with a string value at runtime (names, items, numbers as text)
%dFilled with an integer value at runtime
\GThe currency unit, used inside formatted strings (e.g. %s\G 手に入れた)
@n, #nPlaceholder styles some scripts use; recognized and preserved like %s

Two rules matter when translating these: every token from the original must appear in the translation (MISSINGPLACEHOLDER otherwise), and their order must not change (S.NEEDSTOBEBEFORE.D / D.NEEDSTOBEBEFORE.S) — the game fills them in the original order regardless of where the translation moved them. See Error Codes.

How SLR Translator preserves codes

Three layers work together so the translator model never has to “translate” a control code:

  • Placeholder swapping (DSLR engine). Before a line is sent, the six code families in the MV/MZ table above are swapped for word-like tokens such as {PERSON1}. The tokens are configurable in the DSLR engine options (Placeholders category) — each must keep the $1 that carries the number, and changing them invalidates the translation cache. A separate set exists for the fallback model. After the model answers, the codes are restored from the tokens.
  • Sentence-safe splitting. Text is split into sentences before translation; the splitter treats color spans (\C[…]…\C[…]), leading codes and trailing symbols as boundaries, so a code never ends up cut in half between two sentences. Many placeholder styles are recognized natively (%1, @1, #1, <1>, {1}, @@1@ and more).
  • Recovery and checking. If the model loses a placeholder anyway, the engine re-inserts it — at the start or end of the sentence, or at the best-guess middle position (marked SHISAYE.LOSTPLACEHOLDERMIDDLE so you can verify it). Afterwards the fix-up pass compares every translation against its original and records anything broken in the Errors column.

Escaped rows and the blue tag

Rows that the parser classified as comments or escaped developer text — not text the game shows to the player — carry the blue cell tag. Blue rows are skipped by the batch translator by default. See Cell Color Tags for the full tag system.

When codes break anyway

  • Every detected breakage lands in the row's Errors column as a SHISAYE.* code — the full list with causes and fixes is on the Error Codes page.
  • If a script fragment keeps getting broken mid-sentence, the Aggressive Splitting patterns in the translation engine options control where text may be split — adding an entry for the problematic fragment stops it from being cut. See Custom Parsers & Model Creator.
  • For files with unusual code formats entirely, a custom parser can describe how to extract and protect the text before translation: see Custom Parsers & Model Creator.
