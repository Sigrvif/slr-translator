Encrypted & Packed Games

Japanese RPG Maker games are often distributed in a protected form. SLR Translator handles the common protections during project creation, so the translation workflow itself stays the same. This page describes what happens for each kind of protection.

Packed RGSS archives (XP, VX, VX Ace)

RPG Maker XP, VX and VX Ace games can pack the whole Data folder into a single archive next to the executable:

ArchiveEngine
Game.rgss3aRPG Maker VX Ace
Game.rgss2aRPG Maker VX
Game.rgssadRPG Maker XP

When the wizard finds one of these, it enables Create a development copy marked (required) and you pick a Set development directory. After confirming the copy, the tool:

  1. Copies the complete game into a <Game> Unpacked folder inside your development directory.
  2. Decrypts every RGSS archive in that copy with the bundled decrypter command line tool, writing the extracted files back into the copy.
  3. Removes the archive files from the copy, leaving an editable, unpacked game.

The project is then created from the unpacked copy; the original packed game is never modified.

Choose the development directory outside the original game folder. A development copy inside the game's own directory causes problems when you later apply a translation into it — the wizard rejects such paths.

Enigma Virtual Box executables

Some games ship as a single executable packed with Enigma Virtual Box. Detection recognizes these executables by their .enigma1 and .enigma2 header sections, regardless of engine.

For a packed executable the wizard also forces a development copy. After you confirm, the built-in unpacker extracts the embedded files into your development directory with a progress report, then the tool:

  1. Finds the real game folder inside the extracted files.
  2. Runs engine detection again on that folder.
  3. Creates the project from the unpacked game.

The unpacker is built into SLR Translator and works on Windows and Linux — no external unpacking tool is needed.

Encrypted MV/MZ data files

Protection tools for MV and MZ can replace the JSON files in data/ with encrypted containers. The parser recognizes these containers and:

  • Detects the encryption parameters automatically by reading the game's own script files (rpg_managers.js for MV, rmmz_managers.js for MZ), including WebAssembly-based variants.
  • Decrypts each file for parsing, and re-encrypts the translated files with the same parameters on export, so the applied copy keeps the game's original protection.
  • Skips files it cannot decrypt.
  • Feeds the decrypted data to the Scene Graph as well, so scene-aware batch translation and scene context work for protected MV/MZ games too.
Encrypted MV audio and images (.rpgmvo, .rpgmvm, .rpgmvp for MV; .ogg_, .m4a_, .png_ for MZ) are irrelevant to text translation — they are copied along untouched. For translating text inside encrypted pictures, see SEP Picture Translation.

Encrypted RGSS script containers (TES)

Some protected RGSS games move their scripts into an encrypted Data/main data file (main.rvdata2, main.rvdata or main.rxdata, depending on the engine). When such a file is present, its contents are extracted with the bundled TES patcher during parsing, appear in the project like regular script files, and are rebuilt into the encrypted container when you export or apply the translation.

Working safely

  • All unpacking and decryption happens in the development copy or the staging area — keep the original distribution files untouched as your backup.
  • Before applying a translation into a directory, make sure it does not hold your only copy of the game.
  • Keep an eye on the progress log during project creation and apply: unpacking, decryption and repack steps are reported there, and errors offer to open the page for your game's engine.
