Custom Parsers & Model Creator

When a game or tool stores its text in files no built-in engine understands — subtitle files, config files, custom script formats, tabular data such as CSV exports — the Custom Parser module turns them into a translation project anyway. You describe which files to grab and which parts of their content are translatable with rules made of regular expressions or JavaScript functions, and the resulting project behaves like any other: grid editing, batch translation and export all work as usual.

Ready-made parser models ship in the Custom Parsers folder next to the application executable — including CSV AUTODETECTION for tabular files, TXT_Parser for plain text, and MTOOL ManualTransFile for MTool dumps, plus a collection of older, very specific examples. Load them in the wizard like any other .tpm file.

Parser models (.tpm)

Rules live in a Parser Model — a JSON file with the extension .tpm. A model consists of file groups: each group names a set of files with semicolon-separated glob patterns (for example *.srt or *.txt;*.js;*.json) and carries an ordered list of rules applied to every matching file. A model can hold several file groups, so one project can cover different file types at once.

Starting a custom project

  1. Open New Project and choose the Parse any file with custom parser slide.
  2. Load an existing .tpm model file — or drag and drop the file onto the slide. To build a new model instead, press Create a new model, which opens the Parser Model Creator.
  3. Optionally set a Read Character encoding list (comma-separated, order matters — leave blank to keep each file's original encoding).
  4. Press Select Folder! and pick the folder with your files. SLR Translator parses every matching file, stages copies of them, and opens the project.

Rules

Every rule is one of two kinds:

  • Regular expression — an ECMAScript pattern with modifiers, which capture groups to extract, and an action: Capture value (the group becomes a translatable row), Capture then mask value, Mask value (protect the match from translation), or Send to inner rule (apply a nested rule to the captured text; inner rules can nest further). Rule order matters, especially when masking.
  • JavaScript function — the body of an async function(text, thisModel) receiving the whole file content and the current rule object, with this bound to the parser instance. It returns nothing, one offset pair {start, end}, or an array of them — each range becomes a translatable row.
Two pitfalls called out by the model editor: prefer the + quantifier over *, because zero-length matches break the parser; and beware carriage returns — test tools that silently strip \r will mislead you on Windows-style files.

Parser Model Creator

The Parser Model Creator is a dedicated editor window for .tpm files (also opened by Create a new model in the new-project slide; .tpm files can be dropped onto it). It has a file-group navigator on top and, per group, four tabs:

  • Rules — the ordered rule list; drag to reorder, add or delete rules, and edit the selected rule in the form (pattern editor, capture groups, action; the function editor for JavaScript rules). A breadcrumb tracks where you are while editing nested inner rules.
  • Hooks — two JavaScript hooks per group: To Grid transforms extracted text before it is displayed (function(text, context, parameters); e.g. return JSON.parse(text); to unwrap escaped strings), and From Grid is its inverse, converting the edited cell back on export (function(text, context, parameters, info); e.g. return JSON.stringify(text);).
  • Options — read and write character encodings for the group's files (auto by default).
  • Testing — paste sample text on the left and watch the live preview: the extracted rows in a mini-grid, or the fully patched output after you fill dummy translations (the context menu's dummy translator simply reverses the text). The preview re-runs as you type, so pattern tweaks are verified immediately.

Example: SRT subtitles

A minimal model for subtitle files — a file group *.srt whose single regex rule captures the text lines under each timestamp (capture group 1):

/\d+[\r\n]+\d+:\d+:\d+,\d+ --> \d+:\d+:\d+,\d+[\r\n]+((.+\r?\n)+(?=(\r?\n)?))/g

The same idea as a JavaScript function rule, using the match-indices extension available to scripts (every exec() result carries group offsets in matches.indices):

var result = [];
var regex = /\d+[\r\n]+\d+:\d+:\d+,\d+ --> \d+:\d+:\d+,\d+[\r\n]+((.+\r?\n)+(?=(\r?\n)?))/g;
var matches;
while (null != (matches = regex.exec(text))) {
	result.push({
		start: matches.indices[1][0],
		end:   matches.indices[1][1]
	});
}
return result;

Export

The model is stored inside the project, so exporting needs nothing extra: translations are patched back into staged copies of the original files, honoring the write encoding (each file's original encoding and byte-order mark are preserved unless overridden). Export to a folder or a zip with Export Project — see Exporting the translation.

Splitting patterns (Aggressive Splitting)

The tips mention adding entries to the SplittingPatterns when “a script bit keeps getting broken”. These are not part of custom parsers — they are a translation-engine option called Aggressive Splitting, edited in the engine's options under the Patterns section (see DSLR Translator and Options Overview).

Semantics: every match is split out of the sentence entirely — its position and content are never sent to the translator — and the sentence is cut at each occurrence. That guarantees script calls, control codes and other untranslatable fragments survive translation untouched; splitting out such fragments also improves translation quality and speed. The cost is context: the translator no longer sees the split fragments around the sentence. A large, commented default set covers common engines and game-specific quirks (empty lines, labels, script commands, known system messages); add your own pattern when a specific game keeps mangling a specific code sequence.
